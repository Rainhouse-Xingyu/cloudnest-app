# CloudNest Go 后端功能重构计划书（handler -> service -> storage）

## 1. 重构目标

- 将当前以 `handler` 为中心的实现，重构为清晰的三层架构：`handler -> service -> storage`。
- 目标是“职责分离、可测试、可扩展、可维护”，并保持现有 API 行为与数据结构兼容。
- 本次重构聚焦 `cloudnest/cloudnest_go`，不改 iOS/macOS 客户端。

## 2. 现状检查结论（基于代码扫描）

- `internal/service` 目录为空，`internal/storage` 目录为空。
- 多数业务逻辑、事务、权限判断、数据库读写、Redis 读写集中在 `internal/handler/*.go`。
- `file_handler.go` 体量最大（接口与内部方法最多），集成了上传/下载、分享、回收站、缩略图、日志、限流、自动 AI 分析等多类职责。
- 存在跨模块逻辑重复：如 `canAccessFile` 在多个 handler 内重复实现。
- `cmd/server/main.go` 直接注入 DB/Redis 到 handler，尚未形成 service/storage 依赖注入链路。

## 3. 目标分层与职责边界

### 3.1 Handler 层（接口层）

- 仅负责：参数绑定、输入校验、调用 service、HTTP 状态码与响应格式转换。
- 不负责：业务规则、事务、SQL/Redis 细节、文件系统细节。

### 3.2 Service 层（业务层）

- 负责：业务编排、权限规则、事务边界、跨存储组合、领域校验。
- 对外提供业务接口，供 handler 调用。
- 依赖 storage 接口（而非直接依赖 GORM 细节）。

### 3.3 Storage 层（数据访问层）

- 负责：MySQL/Redis/本地文件系统访问实现。
- 提供面向业务语义的仓储接口（Repository/Store）。
- 不包含 HTTP、Gin 上下文逻辑。

## 4. 目录重构规划

建议新增（或逐步补齐）目录结构：

```text
cloudnest/cloudnest_go/internal/

  service/
```

说明：
- 现有 `internal/store/mysql.go`、`internal/store/redis.go` 保留为基础连接初始化；
- 逐步把“业务查询/更新”下沉到 `internal/storage/*` 中；
- 每个 service 按接口依赖 storage，便于单元测试 mock。

## 5. 按模块功能重构计划

## 5.1 认证与用户信息模块（Auth）

覆盖功能：登录、登出、当前用户信息、管理员判定。

当前问题：
- `auth_handler.go` 同时处理密码策略、管理员角色查询、JWT 生成、Redis token 存储。

重构目标：
- `AuthHandler` 仅保留请求/响应转换。
- 新增 `AuthService` 负责登录流程与安全策略。
- 新增 storage：
  - `UserRepo`：按用户名/ID 查用户、更新密码。
  - `RoleRepo`：管理员角色判定。
  - `AuthTokenStore`：token 写入/删除（Redis）。

实施步骤：
1. 抽离 `Login` 业务为 `AuthService.Login(ctx, req)`。
2. 将 `isAdminUser` 下沉至 `RoleRepo`。
3. 将 Redis token 读写抽到 `AuthTokenStore`。
4. handler 仅做参数校验和错误映射。

验收标准：
- 登录/登出/获取当前用户 API 返回不变。
- Auth handler 内不再出现 `h.DB.Where/First` 与 `h.RDB.Set/Del`。

## 5.2 管理员模块（Admin）

覆盖功能：创建用户、设置路径权限。

当前问题：
- `admin_handler.go` 承担事务、角色初始化、权限组装、日志写入与缓存失效。

重构目标：
- 新增 `AdminService` 管理用户创建与权限更新事务。
- 新增 storage：
  - `UserRepo`、`RoleRepo`、`PermissionRepo`。
  - `OperationLogRepo`。
  - `PermissionCacheStore`（Redis）。

实施步骤：
1. 抽离 `CreateUser` 事务逻辑至 service。
2. 抽离权限覆盖更新为 service 方法（带审计日志）。
3. Redis 权限缓存失效统一走 store 方法。

验收标准：
- 创建用户与权限更新行为一致。
- 权限缓存命中与失效行为保持一致。

## 5.3 文件与存储模块（File，最高优先级）

覆盖功能：文件树、目录管理、上传分片、下载、搜索、分享、移动复制、回收站、缩略图、操作日志、限流、自动 AI 分析。

当前问题：
- `file_handler.go` 职责过重，混合 HTTP、业务规则、事务、DB、Redis、文件系统、压缩流处理。
- 与 AI、Live Photo 模块存在耦合调用。

重构目标：
- 拆分为多个 service 子域：
  - `FileQueryService`（列表/搜索/预览/详情）
  - `FileCommandService`（创建目录/重命名/移动/复制/删除/恢复）
  - `UploadService`（初始化/分片/合并/进度）
  - `DownloadService`（单文件/批量/目录压缩/限速）
  - `ShareService`（创建分享/撤销/公共访问）
  - `RecycleBinService`
- 拆分 storage：
  - MySQL：`FileRepo`、`StorageRepo`、`UploadRepo`、`ShareRepo`、`OperationLogRepo`、`LivePhotoRepo`、`SettingRepo`
  - Redis：`RateLimitStore`
  - FS：`ChunkFileStore`、`ObjectFileStore`、`ZipBuilder`、`ThumbnailStore`

实施步骤：
1. 先抽公共能力：`AccessControlService`、`OperationLogService`、`StoragePathService`。
2. 再按子域迁移接口，优先迁移“读接口”（list/search/download），再迁移“写接口”（upload/move/copy/delete）。
3. 把事务全部收敛到 service，storage 只做数据操作。
4. 将 AI 自动分析触发改为事件式调用（先同步接口，后可异步队列化）。

验收标准：
- 文件相关 API 行为不变。
- `file_handler.go` 显著瘦身（只保留 HTTP 处理和 service 调用）。
- 可针对 service 做单元测试（mock repo/store）。

## 5.4 协作模块（Collaboration）

覆盖功能：工作区创建/成员管理/文件权限/版本管理。

当前问题：
- `collaboration_handler.go` 直接组织事务和权限判定。

重构目标：
- 新增 `CollaborationService` 聚合协作规则。
- 存储拆分：`WorkspaceRepo`、`WorkspaceMemberRepo`、`FilePermissionRepo`、`FileVersionRepo`、`OperationLogRepo`。
- 将角色规则（owner/admin/member）集中到 service policy。

实施步骤：
1. 抽离 workspace 成员管理流程。
2. 抽离文件权限授予/回收流程。
3. 抽离版本创建与并发校验（base version）逻辑。

验收标准：
- 协作权限行为与现状一致。
- 角色判定逻辑不再散落在 handler。

## 5.5 Live Photo 模块

覆盖功能：绑定、自动绑定、解绑、查询。

当前问题：
- 文件可见性判断与文件模块重复实现。

重构目标：
- 新增 `LivePhotoService`。
- 复用统一 `AccessControlService`（避免重复 `canAccessFile`）。
- 新增 `LivePhotoRepo` 与必要 `FileRepo` 组合。

实施步骤：
1. 抽 `canAccessFile` 为共享服务。
2. 迁移绑定/自动绑定规则到 service。
3. handler 仅保留请求校验与响应序列化。

验收标准：
- Live Photo 绑定规则一致。
- 删除重复访问控制实现。

## 5.6 FRP 模块

覆盖功能：设备管理、映射管理、配置预览/保存/回滚/下发、设备状态、命令队列与结果上报。

当前问题：
- `frp_handler.go` 同时操作 MySQL 与 Redis 队列，事务与队列一致性难以测试。

重构目标：
- 新增 `FrpService`。
- 存储拆分：`FrpRepo`（MySQL）、`FrpCommandStore`（Redis）。
- 端口分配、命令入队、历史记录维护作为 service 内独立策略。

实施步骤：
1. 抽离设备/映射 CRUD。
2. 抽离配置生成与版本流转。
3. 抽离命令队列协议（enqueue/pull/report）。

验收标准：
- FRP API 保持兼容。
- Redis key 规则集中管理，可单测命令状态机。

## 5.7 AI 模块

覆盖功能：OCR、智能搜索、自然语言搜索、摘要、助手问答、AI 配置应用。

当前问题：
- `ai_handler.go` 包含 DB 查询、文件读取、EXIF 解析、外部模型调用、元数据入库等混合流程。

重构目标：
- 新增 `AIService`（业务编排）+ `AIClient`（外部模型调用适配）+ `AIRepo`（元数据/任务）。
- 文件读取和权限校验复用 File 相关 service/storage。

实施步骤：
1. 先抽 `AIClient`，统一模型调用与错误处理。
2. 抽 `OCRPipeline`（读文件 -> 调模型 -> 落库）。
3. 抽 `AISearchService`（查询条件组装、分页）。

验收标准：
- AI 结果结构保持一致。
- 外部模型调用失败路径可独立测试。

## 5.8 系统设置模块（Settings）

覆盖功能：系统设置读写、权限摘要、个人速率窗口。

当前问题：
- `settings_handler.go` 含较多事务和聚合查询。

重构目标：
- 新增 `SettingsService`。
- 新增 `SettingsRepo`，并拆出 `PermissionSummaryQueryRepo`（复杂统计查询）。

实施步骤：
1. 抽 settings 的 upsert/read。
2. 抽权限摘要统计查询。
3. 抽个人速率窗口策略。

验收标准：
- 设置读写与摘要统计行为保持一致。
- handler 不再直接持有复杂 SQL 逻辑。

## 6. 公共能力与横切改造

- 统一错误模型：`ErrNotFound/ErrForbidden/ErrConflict/ErrInvalidInput/ErrInternal`。
- 统一权限判断服务：避免多处重复 `canAccessFile`。
- 统一审计日志服务：业务层记录，storage 落库。
- 统一事务模板：service 使用 `TxManager` 包装事务，减少重复样板代码。
- 统一依赖注入：在 `cmd/server/main.go` 完成 repo -> service -> handler 的组装。

## 7. 分阶段实施计划（建议顺序）

### 阶段 A：地基建设（1~2 天）

- 建立 `service`/`storage` 目录与接口骨架。
- 建立公共错误、事务管理、日志接口。
- 在 `main.go` 引入依赖注入骨架（保持旧 handler 可运行）。

### 阶段 B：低风险模块先迁移（2~3 天）

- Auth、Admin、Settings 先改造。
- 每迁移一个模块即做回归测试（接口级）。

### 阶段 C：中复杂模块迁移（3~4 天）

- Collaboration、Live Photo、AI 模块。
- 合并重复权限判断逻辑。

### 阶段 D：核心大模块迁移（5~7 天）

- File 模块分子域逐步迁移（读路径 -> 写路径 -> 上传下载 -> 分享与回收站）。
- 最后迁移 FRP（含 Redis 队列状态机）。

### 阶段 E：收尾与优化（2~3 天）

- 清理废弃函数与重复代码。
- 增加 service 单元测试与关键接口回归测试。
- 输出架构说明与后续开发规范。

## 8. 风险与应对

- 风险：接口行为回归偏差。应对：模块迁移完成后立即跑接口回归（按路由清单）。
- 风险：事务边界变化导致数据不一致。应对：先迁移只读，再迁移写事务；关键流程保留对照测试。
- 风险：Redis key 兼容性。应对：统一 key 常量并保持旧 key 规则不变。
- 风险：文件系统路径处理回归。应对：为上传、下载、打包、缩略图建立端到端样例测试。

## 9. 完成判定标准

- 代码层面：handler 中不再出现主要业务逻辑与直接 SQL/Redis 细节。
- 架构层面：所有核心功能具备对应 service 与 storage 实现。
- 质量层面：关键业务具备 service 层单测，主要 API 回归通过。
- 交付层面：形成可持续开发规范，新功能默认按三层架构落地。
