# 原生 FRP 命令与回执恢复

G09 的设备详情现提供部署指定配置、启动、停止、重载和诊断。每次先确认设备与操作，调用既有生产命令 API；没有新增绕过权限的执行入口。配置预览/生成/回滚、设备/映射/服务器编辑及 enrollment 仍继续实施，本批不代表 FRP 原生功能全部完成。

## 提交与恢复

确认时捕获服务器和用户身份，实际提交前再次验证。每个操作生成不可变 request_id，先将身份、设备、action、config_id 写入私有本地 journal，再发送 HTTP。没有收到可信回执时显示“结果未确认”，不能据此推断服务器未接收。再次打开应用只恢复记录，不自动重放远程操作；“使用原请求重试”保持原键和全部操作参数。收到回执显示“服务器已接收”，执行是否成功仍以服务器命令状态和 Agent 回执为准。

相同设备的在途操作互斥，同一未确认操作不能换新键重复创建。账户/服务器切换取消旧请求，旧记录按身份隔离；403 保留登录，未确认记录和原键继续保留。“停止本地重试”只放弃本地重试，不取消服务器任务，确认框和记录明确提醒核对远端状态。退出中的 manager 取消并等待在途任务，再关闭 journal；正面回执保存失败时保留其内存事实并禁止继续提交，不能降级为未发送。

`FRPCommandStore` 使用进程独占 flock、目录描述符相对操作、0600 独占临时文件、文件 fsync、原子 rename 和目录 fsync。校验不可变字段与递增 revision，已接收记录不能降级或替换 command_id。拒绝符号链接/硬链接记录、未知文件、坏数据和过大条目，保留原字节，不自动清理历史。单条上限 16 KiB，总条目上限 1024，崩溃临时文件也占额度；达到上限停止新提交。目录同步结果不确定则关闭后续写入，要求重新打开核对。此实现和测试不等于完成真实断电/磁盘缓存耐久验收，归档界面与 G10 故障矩阵仍待做。

## 真实服务与 GUI 证据

普通 Swift 新增五项存储、三项 manager 测试，覆盖原键恢复、进程互斥、目录路径替换、坏/链接记录保留、容量限制、先落盘后 HTTP、并发关闭、旧确认跨服务器拒绝。独立真实 TLS/Go/MySQL/Redis 用例在生产事务成功后故意截断 HTTP 响应，客户端重开并用原键取得同一个命令；服务端仅一条记录，同时验证受限账户 403 与本地放弃。测试专用传输故障不伪造业务响应。

GUI 使用实际编译的 Agent 0.3.0、固定官方 frpc/frps 0.71.1 与独立 loopback 服务。原生按钮依次部署、诊断、停止、启动、重载，五个命令全部实际 succeeded、attempts=1。部署/诊断/启动/重载后分别验证真实 TCP、HTTP、HTTPS 到达独立上游，HTTPS 校验私有 CA 和域名；停止后验证 TCP 监听消失，不将仍共享的 HTTP/HTTPS frps 监听误报为关闭。运行页显示真实三条 registered 与本地探测采样。

- [首轮报告](MACOS-FRP-COMMAND-GUI-INITIAL-20261121.json)保留 passed=false：五操作通过，但完整运行信息挤出了详情关闭按钮。修复滚动内容和固定页脚的布局优先级。
- [最终报告](MACOS-FRP-COMMAND-GUI-FINAL-20261121.json)绑定最终 App/Core/二进制指纹，实际点击可见关闭按钮；正常退出后将私有 reload journal 恢复为预制“未确认”检查点，再开应用点击原请求重试。全部五条服务端回执（包括完成时间）完全不变，没有新增命令或增加执行次数，原 command_id 恢复。本项是检查点注入，不声称发生了实际崩溃/网络丢包；真实 HTTP 丢回执由上述独立 Core/Go 用例验证。
