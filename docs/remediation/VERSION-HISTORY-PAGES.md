# 版本历史分页

新版原生历史窗口每次请求、解码及显示最多 50 项，翻页替换当前页，不把全部历史累积到内存。响应体限制 512 KiB。提供“较早版本”“较新版本”，刷新返回最新页；下载/恢复只针对页面中确认的记录，恢复与上传仍使用独立捕获的当前版本。

## HTTP 协议

`GET /api/files/:id/versions?page_size=50` 返回原有 file_id、current_version、items，另有：

```json
{"page":{"size":50,"snapshot_version":56,"has_older":true,"has_newer":false}}
```

page_size 是 1–100 的正整数。下一较早页使用 `before_version=<本页最小版本>`，较新页使用 `after_version=<本页最大版本>`，并带首次取得的 `snapshot_version`。两个游标不能同时提供，游标必须大于 0 且不超过快照版本；续页必须带快照，首请求不能指定快照。严格拒绝重复、未知、空、非规范整数、溢出和错误编码的参数，返回 400。

SQL 利用既有 file_id/version 唯一索引进行 seek，不使用 OFFSET。向较新页查询时按升序取最近 N 项，再倒序返回，避免跳回最顶页而漏掉中间页。版本号有缺口同样可以遍历；两个 EXISTS 检查标记当前范围之外是否还有历史。单次请求保持相同的只读 Repeatable Read 授权/文件头/历史快照。

每次请求重新检查活动文件和树权限；旧游标不是访问能力。请求快照与当前版本不一致时返回 409。原生清空旧列表/基线并要求刷新，未自动重试或混用新旧页面；撤权后拒绝下一页。此快照号不是长期数据库快照：旧库人工改写/删除历史而不推进头版本不在这个并发约定内，应停写维护并重新打开窗口。

## 兼容与限制

无查询参数的旧调用保持完整 items 响应且没有 page 字段，没有对旧客户端静默截断。这个遗留路径仍可能返回大量历史，后续 API 版本升级需要明确迁移和资源预算，不能把本批描述为所有客户端的历史内存问题均已解决。未知查询现在拒绝，避免把拼错的分页参数当成无界旧调用。

新版原生要求页元数据、正确文件 ID/快照、50 项上限、严格倒序及唯一记录、游标内范围和合法导航标记；缺失或不一致响应拒绝，不回退旧无界请求。部署须先升级后端，再升级客户端；旧产品仍可读新后端原无查询响应。本批不新增字段、迁移或生产数据写操作。

## 证据

- 两项新增真实 MySQL/API 用例：125 条非连续历史的完整双向遍历、旧响应不截断、撤权、推进版本后旧游标 409、刷新看到新代次；另覆盖重复/溢出/缺少快照/矛盾游标及未知参数拒绝。
- 既有并发追加用例同时核对有界页与头版本来自同一快照。共 4 项历史 race 通过；最终测试时间按 G08/PR 的精确记录核验。
- Swift 响应校验测试覆盖错文件、重复/未来版本、负大小、缺页元数据、错快照、乱序、无界元数据、矛盾导航及游标外记录拒绝。
- 真实 Swift/Core/Go 联调经实际恢复追加至 56，验证 50 项最新页、6 项旧页和相邻较新页；再追加至 57，旧续页被拒绝、列表清空，刷新恢复 50 项。身份退出后旧窗口不能继续读。
- 本机原生窗口实际显示 56 的页范围 7–56 → 1–6 → 7–56，正确禁用边界按钮；专用应用退出及临时服务停止已核对。GUI 用 `CLOUDNEST_NATIVE_UI_VERSION_PAGES=1` 创建历史，开关仅在手动隔离 integration 夹具内，经实际 API 追加，不进入产品路由或目标。

历史分页不完成旧缓存、批量/异常 GUI、主题/尺寸、资源基准、备份恢复或整个 Goal。精确提交的远端 CI 继续单独核对。
