# 容量计量、账本与上传预留

2026-10-22，G02/G03 基础。配额现在约束真实元数据发布，不能只显示一个使用百分比。本轮仅在 disposable MySQL/Redis 和临时文件验证，未迁移真实库。

## 计量策略 retained_file_objects_v1

额度仍按现有配置语义：storage_quota_bytes 优先，未设置时使用 storage_default_quota_bytes；两者是应用于每个用户的额度配置，不是全服务器共享磁盘池。都未设置则无用户额度限制；已存在但非法、非正或超出支持范围的配置返回 503，不静默变成无限制。

| 内容 | 计量规则 |
|---|---|
| 当前普通文件指针 | 以 storage.file_size 计量；沿用当前文件读取能力，不等于证明旧库来源或重新扫描旧磁盘 |
| source_verified=true 历史 | 与当前指针按 (file_id, storage_id) 合并，单个文件同一对象只计一次 |
| 回收站 | 继续计量当前及已验证历史，永久删除最后相应文件引用后释放该文件额度 |
| 复制 | 新 file_id 独立计量，物理去重不免除逻辑副本额度 |
| 版本恢复/重复内容版本 | 已被此文件保留的同一对象不重复计量；新保留对象增加额度 |
| 共享写入 | 计入目标文件所有者，而非操作的协作者；来源授权仍独立验证 |
| 未证明的旧历史/异常目录指针 | 继续保留 GC 引用，单独报告未计量组数；不推断所有者、不泄露外来对象尺寸、不自动收费/删除。另一已验证版本或当前指针持有相同对象时，该文件对象组仍正常计量 |

没有对应 file 的旧版本不能自动归属某用户，仍由完整引用图保留，需后续旧数据审核。旧的元数据专用行若没有 storage 指针，不凭声明 size 猜出一个物理对象。本策略的 used_bytes 是已计量逻辑内容，**不是磁盘占用、全部旧历史或临时分片的总大小**。当前指针及已验证历史中存储尺寸 NULL/负值或缺失对象元信息时返回 503，不能把异常内容当成零使用量。

active_bytes 是活动文件当前内容；history_bytes 是活动文件其他已保留内容；recycle_bytes 是回收站文件全部已计量内容。三者相加为 used_bytes。unmetered_references 是本用户现存文件中尚未计量的对象组数，不是未知对象字节数。

## 事务账本与锁顺序

新增 user_storage_ledger 保存 used/reserved/unmetered、accounting_valid、revision 和更新时间。它是事务内重算的缓存及审计状态，**不是配额判断的权威来源**：每次分配/发布都从文件、版本及有效预留重新计算。概览使用只读 REPEATABLE READ 快照，不盲读缓存，也不修改文件/账本。手动篡改缓存计数不能产生新的可用额度。

所有内容计量变更先共享锁定 storage_quota_policy 单例，再锁对应用户账本，随后进入既有命名/任务/文件锁。不同用户可持共享策略锁并行分配；相同用户串行。复制、版本创建/恢复、上传完成与永久删除的元数据、计量缓存和 quota_accounting 审计同事务，失败全部回滚。版本操作先核实可写所有者，锁后再次核对；客户端不能选择被计量用户。

所有系统设置写入口（包括批量及 AI 管理设置入口）先独占同一策略锁。这样数据库排序规则视为同名的大小写/其他键变体也不能绕过配额配置顺序。设置写入因此可能等待已有内容事务；大文件完整性校验目前仍可能延长锁持有时间，尚未完成规模压测。

已有额度被管理员降低时，不自动删除文件或取消预留。新的分配和完成/版本发布重新检查当前额度，超限 507；已保留文件可以继续读取、移到回收站、恢复回收站或永久删除。发布检查采用当前总量规则，已超限时即使某次版本恢复不增加已计量字节，也需先释放空间。取消和永久删除不要求配置值可用，允许用户从异常/超限状态中释放资源；账本若有异常尺寸会明确标为不可依赖，不把缓存部分和当作有效概览。

## 上传预留与固定契约

新任务 contract_version=1，初始化持久化 parent_id、总字节、分片尺寸/数量与 reserved_bytes，期限由数据库 UTC 设为 24 小时。计算 ceil(total/chunk) 使用无加法溢出的整数公式；显式数量必须匹配，负数或超过数据库整数字段范围的请求 400。

在同一账户锁内创建任务、重算 used+所有有效 reserved 并检查额度；超限返回 507 且不留下新任务/预留。初始化及恢复都检查目录资格；恢复必须匹配已存名称、尺寸、分片参数和父目录，不再把一个任务挪到其他目录。旧 contract_version=0 任务不自动获取预留或继续发布，返回 409，旧任务与分片保留，客户端需新建任务。

完成在原有唯一候选/哈希验证/任务锁内核对当前预留和目录，并用含状态/期限/预留/目录条件的 CAS 转为完成、释放预留，同时发布 file/version、更新账本及审计。长校验期间跨过期限同样不能绕过最终状态检查。失败保留预留和分片供合法重试，未采用的本次候选按既有确定提交规则清理；未知提交结果仍保留待对账。完成结果复用尚未实现，重复完成仍为 409。

预留在 expires_at 过后立即不参与有效额度；迟到完成/分片元数据提交拒绝 409。下次同用户初始化会把已过期的新协议任务持久化为 status=4/reserved=0，并审计。没有后台全局过期扫描；因此未再写入的旧任务行可能仍有原始 reserved_bytes，必须结合状态/期限计算，不能简单 SUM 全表缓存字段。

新增 POST /api/files/upload/cancel，JSON 为 upload_id。仅本人可取消，首次状态改为 3、释放预留并审计；再次取消幂等 200，已完成任务 409，其他用户 403。客户端 user_id 不决定归属。取消与完成使用相同账户/任务锁，只有一个成功。取消不执行文件树删除，已有分片留给 G03 的持久对账/清理，不能凭路径猜测安全删除。任务状态 2 为后续暂停保留，目前未实现暂停/继续控制接口，不作为已完成功能。

## API 与兼容

GET /api/storage/overview 保留原字段，并新增 reserved_bytes、available_for_upload_bytes、active_bytes、history_bytes、recycle_bytes、unmetered_references、accounting_policy。remaining_bytes 仍为额度减已计量使用量，available_for_upload_bytes 再扣有效预留；无额度时 has_quota=false，不能把数值 0 当作“禁止上传”。未知/异常计量返回 503，而不是一个伪造空概览。

冻结 iOS 的 UploadInitRequestDTO 本来已发送 parent_id、名称、总尺寸和分片参数，普通、后台和 Live Photo 上传也捕获父目录，新增契约与这些请求形状一致；没有修改 iOS 源码。旧未完成任务、错误分片数量、改变参数续传以及 24 小时后恢复的行为收紧已明确。旧容量 UI 若只看 remaining_bytes，可能低估预留占用，最终由服务器 507 拒绝；macOS 必须使用 available_for_upload_bytes 并区分 409/507/503。新增取消路由仍需自定义权限账号精确授权；57 项旧路由快照不扩充伪称客户端已支持新功能。

## G03 上传临时预算补充

新分片和合并候选另有持久物理临时卷预算，默认种子 8 GiB，实际额度以卷记录为准。此预算不会改变逻辑用户预留；合并时同时计入分片与完整候选，可能另返回 507。取消/到期先释放逻辑预留，物理字节只有在证明可删除并最终提交 done 后释放临时额度。ZIP/缓存不在当前范围，详见 [临时对象协议](TRANSFER-REGISTRY.md)。
