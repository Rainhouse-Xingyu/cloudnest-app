# 文件对象发布与版本引用整改

G02 进行中。基于 `5dbb7c1`，沿用 SHA-256 对象去重和既有 MySQL 模型；本批没有启用物理 GC。测试仅使用 disposable 数据库与临时文件。

## 修复前证据

三个新增真实 API 用例在修复前失败：

- 同一 upload_id 的两个完成请求均返回 200，产生两条逻辑文件记录；已发布文件随后下载 404。合并复用同一路径，后来的去重逻辑把该路径作为“多余文件”删除。
- 两用户同时上传相同内容，storage 哈希的唯一键竞争使一个请求返回 500。
- 首次上传没有 file_version 记录；更新只写新版本，原始内容没有历史引用。复制还继承来源版本号，却不复制对应历史。

并发用例通过 GORM 回调控制实际 SQL 写入时序，未替换数据库或文件 I/O。去重用例初版清理回调早于后台 AI 结束，测试夹具自身产生 race；修正为等待所有成功请求的后台终态后，再次运行仍复现产品 500，且不再有该夹具 race。该夹具错误不计为产品漏洞证据。

## 发布与去重

合并每次用 CreateTemp 创建独立、权限 0600 的候选对象，不再按 upload_id/逻辑名称覆盖物理路径。流式合并计算 SHA-256，处理写入/关闭错误，Sync 文件与所在目录，再进入数据库事务。合并失败只清理本次尚未进入数据库的候选路径。

完成事务在目录范围锁内锁定并重读上传任务，验证归属、未完成状态、声明总字节数与合并结果。确认完成后后来的请求返回 409，不重复创建文件。storage 使用唯一哈希约束的冲突安全插入，再锁定选中的对象，避免两个所有者的名称锁不同导致 500。

候选、去重对象以 64 KiB 缓冲流式校验实际尺寸与 SHA-256，支持上下文取消；不会仅因哈希记录存在就引用缺失字节。数据库事务不删除物理对象。成功提交后只清理本次未被采用的候选文件；已确定未发出提交的事务失败也可清理本次候选。提交结果不确定时保留候选与分片，等待后续对账，不冒险删除可能已被引用的对象。

若旧对象不可读、缺失或校验失败，而新候选的服务端哈希与旧记录一致且尺寸相同，可以同事务把 storage.file_path 指向新候选并记录 storage_repair。旧路径保留，所有指向同一 storage ID 的文件/版本恢复读取；不能传入客户端自称的哈希来触发修复。元数据尺寸不一致时拒绝，未自动修改旧尺寸。

upload_complete、storage_repair 审计与文件、初始版本、任务状态同事务提交，审计失败完整回滚。已提交后的临时路径/分片清理失败记录待处理审计；审计也不可用时记录无私有路径的服务端日志，不把已提交的上传伪装为失败。

## 版本历史与接口

| 方法与路径 | 行为 |
|---|---|
| `POST /api/files/:id/versions` | 保留原请求格式；当前文件写权限与活动自有来源文件授权仍必需，不接受任意 storage ID 作为能力 |
| `GET /api/files/:id/versions` | 返回持久版本列表，新增 file_type、source_verified 字段 |
| `GET /api/files/:id/versions/:version/download` | 当前文件可读、版本确实属于该文件，且对象完整时流式下载历史字节 |
| `POST /api/files/:id/versions/:version/restore` | body 为 `{"base_version": 当前版本号}`，逐项验证文件写权限；把该文件的历史内容追加为一个新版本，不覆盖旧行 |

新上传保存版本 1；复制只复制当前内容，创建独立版本 1，复制者为作者，不继承来源历史或版本计数。版本创建/恢复在目标行锁内比较 base_version，冲突 409；元数据事务遇到死锁有限重试。版本创建/恢复审计和当前指针、历史行同事务，失败回滚。

旧文件缺少当前版本行时，在下一次版本写入前保留当前可验证快照。只记录当时实际存在的版本号，不编造更早版本，未知作者为 NULL，Comment 明确是保留的旧当前快照。已有历史行不会因本批迁移被重写。旧历史缺少 file_type 时，恢复按目标文件名扩展名提供当前类型回退；不能恢复此前从未保存且已丢失的字节。

已验证来源的历史读取使用当前文件的 owner/显式 read/write 权限，恢复要求 owner/显式 write；失去授权或删除到回收站后历史接口也被拒绝。恢复只接受文件内的版本号，额外 storage_id 不能选择其他文件。当前文件的共享读权限包含其已保存历史，此语义需要在 G07/G09 UI 清楚展示。

### 旧版本来源不能自动视为可信

G01 修复前的版本接口允许任意 storage ID，旧关联本身不能证明来源授权。新上传、复制、经过来源授权的版本发布/恢复，以及显式写入前保留的已可读当前快照，才由服务器置 source_verified=true。客户端字段不能设置或提升该标记。该标记证明当次发布的内容权限，不证明原始作者或升级前任何时期的来源合法。

升级时旧记录默认 false，不批量认定可信。旧历史仅在调用者已能读取同一 storage 的活动文件（owner/显式 read/write），或它就是该文件的当前内容时允许读取/恢复；恢复时重新锁住来源文件和权限。只读 GET 不偷偷提升标记。无当前内容授权的未知历史返回 403，需真实库来源审计/审核处理；不会因为新下载接口而重新开放旧任意引用漏洞。旧 current 指针本身的来源也可能需人工审计，本批没有自动修改这些历史授权关系。未验证的历史仍是应保留的引用，403 不代表允许 GC 删除其对象。

新增路由是普通业务能力；自定义路径授权仍需显式授予相应方法和具体路径/已有前缀通配符，不绕过资源级 ACL。自定义路径仍按具体 URL 或已有前缀通配符匹配，不把 Gin 的 :id/:version 当作授权占位符。原冻结 iOS 57 条 API 快照保持不变。

## 升级与限制

新增可空 `file_version.file_type` 与默认 false 的 `source_verified`。需备份、停旧实例、在副本验证后显式 `migrate` 增加字段，再按原步骤审计并安装/验证名称约束。普通启动发现字段缺失会拒绝服务，不自动迁移。新旧发布不能混跑，以免旧合并/去重代码继续覆盖或删除对象。

当前并发完成的失败方返回 409，尚未提供 G03 所需的持久完成结果复用；upload_id 的 parent_id 契约、分片原子写入/尺寸与数量、暂停/取消/过期、请求预算、未知提交状态恢复仍待完成。总字节校验不等于完整传输协议验收。

文件系统与 MySQL 仍不是统一事务：进程中断/提交结果不确定可能留下候选对象。对象的 .upload-* 名称不代表可以删除，已提交对象也使用该名称，后续对账必须按引用判断。GC 前仍需完整引用图/对象状态、读取租约、延迟回收和崩溃对账；不得按文件年龄或路径前缀直接清理。回收站及历史版本继续保留物理引用，永久删除元数据也未触发物理删除。

现有完整性校验会多次顺序读取对象，大文件吞吐/锁时长未压测；流式实现不等于已经证明大文件性能。普通当前文件下载/AI/预览没有新增全量校验或读取租约；版本变更的 AI 增量索引更新仍属于 G04。目录继承、配额、其他操作可靠审计仍在对应阶段。
