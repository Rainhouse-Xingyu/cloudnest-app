# 显式托管对象与分阶段 GC

2026-10-22，G02。此前持久引用和读取租约已接通；本批增加真实隔离、回收执行和中断恢复。只在新建的 disposable 数据库和临时目录执行过，未对项目真实数据库或历史文件运行。

## 可回收来源

新发布候选位于 storage 根下的 .managed-v1/YYYYMM/blob-<256-bit-random-token>，以锚定 os.Root、O_EXCL 和 0600 创建；目录逐层验证，不跟随符号链接，不接受组/其他用户可写的根、数据目录或路径组件，不自动 chmod 既有目录。文件和相关目录完成 Sync 后才提交元数据。

storage 增加 managed、managed_root、managed_path、orphaned_at、gc_token、gc_path、quarantined_at。旧行默认 managed=false、路径属性为空，**不按名称、年龄或目录位置自动认领**。即便旧行恰好具有新式文件名，也不被 GC 选择。候选必须有显式托管标记、与此次根完全一致的规范路径及可验证的 SHA-256/尺寸。

已验证上传修复不可用对象时，新路径记录为托管对象，旧路径另存 storage_garbage 的 retained 记录；修复路径、引用和审计在同一事务。retained 永不进入自动删除，即使 storage 父记录以后被回收。引用中仍含回收站、目录上的历史指针、未知来源版本和活动读者，不以来源未知为理由取消保留。

## 两段宽限期与状态

| 阶段 | 前提与动作 |
|---|---|
| active，无引用的首次观察 | 在父记录 X 锁内确认 file、所有 file_version 均无引用、无有效读取租约；记录数据库 UTC orphaned_at 与审计，不移动文件 |
| 至少 24 小时后 | 再次锁定检查，持久化 quarantining 意图、随机 token 和 .gc 隔离路径；随后校验内容，以不覆盖目标的硬链接、目录 Sync、删除原链接完成隔离 |
| quarantined | 持久记录 quarantined_at 和隔离审计；再保留至少 24 小时，不立刻删盘 |
| 最终检查 | 重新校验隔离内容，在父记录 X 锁内再次检查全部引用/有效租约，清理该对象的过期租约；同事务创建 pending 回收记录、写 tombstone 审计并删除 storage 父记录，外键作最终保护 |
| 已确认上述事务提交 | 根据持久 pending 记录删除隔离链接、Sync 目录，再记录 done；父记录不存在及已持久回收记录是物理删除前置，未知提交结果不授权删除 |

每次最多处理 64 个对象和 64 条既有 pending 记录，按数据库状态继续；不是循环扫盘，也不是“本次成功即整个存储根已清空”。宽限期固定，无 CLI/环境变量绕过。上传重新使用 active 去重对象时清除旧 orphaned_at；已有文件/版本链路本身一直保留其对象。

新增引用或有效租约出现在隔离状态时，下一次 GC 持久化 restoring 意图，恢复原链接后重新置 active；期间读取返回 503。正常发布/读取不进入不活动对象，外部仍遵守外键的旧写入者也不能让最终删除越过新引用。永久删除 API 仍只删逻辑元数据，不同步删盘。

损坏、路径矛盾、不同 inode 的已存在目标或符号链接进入 blocked/失败报告，保留当前所有链接，不覆盖或自动修理。后续执行仍报告 blocked 数并非零退出；需人工审核。相同 inode 的双链接中断可确认后完成移动。原名已不存在但隔离名存在时可恢复隔离状态；父记录已经消失而 pending 仍在时，可继续完成删除/补记。

## 操作者命令

在停旧实例、备份、副本演练和结构审核后，用新程序显式 migrate 增加上述字段、索引和 storage_garbage。旧对象仍不认领；名称与引用约束迁移照原顺序执行。正常启动检查完整新结构，不自动升级。基础模型迁移尚未全部纳入版本 ledger，完整框架与真实升级/回滚演练仍属 G10。

```sh
./cloudnest audit-storage-references
# gc-storage 必须显式设置 DATA_DIR；使用已配置 MYSQL_DSN 的维护账号。
./cloudnest gc-storage
./cloudnest prune-read-leases
```

gc-storage 不采用默认 DATA_DIR，不创建不存在的存储根；DATA_DIR/storage 必须是对应的私有本地根。维护账号和 Redis/JWT 无关，JSON 仅输出计数、失败对象 ID/阶段，不输出私有路径/正文。未解决对象或预检失败非零退出。没有部署 cron/自动 GC，也没有自动回滚/解除 blocked 的命令。

prune-read-leases 单独按数据库时间最多清理 256 条已过期内部 token，覆盖未托管旧对象，返回实际删除数；不删除文件/版本/storage，不清空租约表。并发续租在行锁后重新检查期限，过期 token 不复活。

## 元数据可见性与数据库契约

物理 GC 除检查最终列、索引、checksum 和全部已知 RESTRICT 外键，还要求维护账号直接具备覆盖此库的 SELECT/TRIGGER（或相应全局直接授权），并能用 PROCESS 查询全局 InnoDB 外键清单。仅角色/逐表授权目前不自动推断，证明不足就拒绝。**不要为普通运行账号追加这些维护权限**；操作者应使用独立维护连接，程序不自行 GRANT。

这是因为 [TRIGGERS 元信息需要 TRIGGER 权限才可见](https://dev.mysql.com/doc/refman/8.0/en/information-schema-triggers-table.html)；[全局 INNODB_FOREIGN 清单需要 PROCESS](https://dev.mysql.com/doc/refman/8.0/en/information-schema-innodb-foreign-table.html)。不能把低权限账号看到的空列表当成无触发器/无外键。全局清单用于排除跨库/隐藏入边，再核对已知三条 file/file_version/storage_read_lease 保留边、当前库所有 storage_id 列及相关表触发器。未知入边、未受约束的新引用列、级联或相关触发器均拒绝执行，不自动移除。GC 当前只支持用于内部清单匹配的简单 ASCII 库名；库名/大小写无法精确匹配时拒绝。

数据库授权中的模式按区分大小写、显式转义匹配实际库名，避免误拒转义库名，也不把不同大小写的授权误当成完整可见性。要求全局和会话 foreign_key_checks=1；不能关闭约束强行回收。所有管理对象的写入者必须遵守不可变路径/托管元数据/租约协议；不支持同时改 DDL、人工复用 ID、篡改路径或移动数据根。没有外键、名称也不遵守约定的任意自定义引用语义，仍需真实库审核，不能由自动预检推断不存在。

## 恢复和保留边界

- 在移动后、隔离状态提交前中断：quarantining 意图仍在，原名/隔离名/双硬链接决定恢复动作，不丢弃字节。
- tombstone 审计或最终外键失败：父记录、回收记录和过期租约清理一起回滚，隔离文件保留。
- 父记录删除事务结果不确定：不立即 unlink；重试从数据库里实际存在的 pending 记录核实父记录已消失再处理。
- unlink 后 done 更新失败：父记录删除和 pending 已先持久化；重试接受已缺失的隔离文件，Sync 后补记完成。相同哈希的新上传用新 ID/新路径，不被旧回收记录误删。
- 无托管标记、旧修复路径、上传未知提交留下且无可证明登记的候选、异常块均保守保留。没有“按 .upload-* 或 .managed-v1 前缀清目录”的命令。

使用受控本地私有根、同一文件系统的硬链接和目录 Sync；不支持的文件系统保留并报错，不回退为不安全复制删除。实际进程 kill/power-loss、NFS/SMB、挂载替换和大文件规模压测尚未完成；本轮用真实文件系统和数据库错误注入验证各提交/链接窗口，不把注入测试称作真实断电实验。现有日志/retained/done 历史没有自动清理策略。

## 验证

新增 16 项集成（含多个子场景）：完整两段宽限期及审计、回收站/未知旧版本/活动读者保留、新引用恢复、移动后状态提交失败、tombstone 审计回滚、unlink 后完成记录失败、新同哈希对象不受旧记录影响、损坏/符号链接/越界、旧路径/错误根/可写目录拒绝、六操作者串行、过期租约 256 条上限与活跃 token 保留、未知/级联/未约束引用/真实触发器及低权限隐藏元信息拒绝、真实 CLI 根要求与物理回收、旧结构升级不认领、相同/不同 inode 目标、最终 FK 失败回滚和旧修复路径保留。

集成脚本只给本次新建的 disposable MySQL 增加 PROCESS 和测试触发器创建配置，并建立仅 SELECT 的对照账号；不向项目既有服务授权。元数据权限首轮定向测试暴露库级授权的严格等值核对误拒合法夹具，改为数据库授权模式核对后重跑；前期通过不冒充最终结果。最新完整结果见 [测试记录](TESTING.md)。
