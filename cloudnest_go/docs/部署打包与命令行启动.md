# CloudNest 后端打包与命令行启动

更新时间：2026-10-22

## 安全升级说明（G01）

构建需要 Go 1.26.10 或更高兼容版本。发布物是 Go 后端程序，不是 macOS 桌面 App。

`MYSQL_DSN` 和 `JWT_SECRET` 必须显式配置；JWT 密钥至少 32 字节，不接受示例占位值。可以在本机用 `openssl rand -hex 32` 生成并保存到受保护的 `.env`，不要把密钥放进命令参数、日志或 Git。`.env` 建议权限 `0600`。默认密码和历史明文密码不再允许登录。

普通启动现在只连接数据库，**不会创建表、修改表或创建管理员**。新安装流程：

1. 配置连接和随机 JWT 密钥，确认目标是新建空数据库。
2. 操作者明确执行 `./cloudnest migrate` 应用当前模型结构。
3. 运行 `./cloudnest audit-file-names`，确认预检成功后显式执行 `./cloudnest migrate-file-names` 安装活动名称唯一约束。
4. 以不回显方式读取 `CLOUDNEST_BOOTSTRAP_PASSWORD`，导出后执行 `./cloudnest bootstrap-admin`，然后立即 unset。密码需 14–72 字节；该命令只接受空用户表，不覆盖已有账号。
5. 启动后用新密码登录。

例如在 Bash 中交互读取引导密码（不将密码写入 shell 历史）：

```bash
read -r -s -p 'New administrator password: ' CLOUDNEST_BOOTSTRAP_PASSWORD
export CLOUDNEST_BOOTSTRAP_PASSWORD
./cloudnest bootstrap-admin
unset CLOUDNEST_BOOTSTRAP_PASSWORD
```

已有部署必须先备份并审核差异，再决定是否执行 `migrate`；它目前仍是显式 AutoMigrate，**不是覆盖全部模型的版本化可回滚迁移系统**；G02 活动名称唯一约束由独立版本化命令管理。不要为重新引导管理员清空用户表。本次增加 user.auth_version，普通启动缺少字段时会拒绝启动。旧 admin/admin、明文账号使用受控 `reset-password <用户ID> <精确用户名>` 命令逐个恢复，密码从标准输入读取，事务内同时撤销全部旧会话并写审计；不要直接 SQL 修改密码。详见 [账号恢复指南](../../docs/remediation/ACCOUNT-RECOVERY.md)。上线时更换 JWT 密钥以使旧会话失效。

已提交过的示例 MySQL/Redis 凭据如仍有效必须轮换；改示例不能撤销历史泄露。生产轮换和数据迁移未在本轮执行。完整验证与剩余风险见仓库 `docs/remediation/G01-SECURITY.md`。

## 1. 启动方式
程序支持以下启动命令：

1. 默认环境变量启动
- `./cloudnest`

2. 直接传端口与文件目录
- `./cloudnest <port> <data_dir>`
- 示例：`./cloudnest 8080 ./data`

3. 带 start 子命令
- `./cloudnest start <port> <data_dir>`
- 示例：`./cloudnest start 8080 /var/lib/cloudnest`

4. 查看帮助
- `./cloudnest -h`
- `./cloudnest --help`
- `./cloudnest help`

5. 查看版本
- `./cloudnest version`

## 2. 参数说明
- `port`：监听端口，必须是 1-65535。
- `data_dir`：文件数据根目录（上传分片、存储文件、缩略图都会在该目录下）。

运行时目录结构示例（`data_dir=./data`）：
- `./data/chunks`
- `./data/storage`
- `./data/thumbnails`

## 3. macOS / Linux 打包

### 3.1 使用 Makefile
在 `cloudnest_go` 目录执行：

1. 当前平台构建
- `make build`
- 输出：`dist/cloudnest`

2. 构建 macOS 双架构
- `make build-macos`
- 输出：
  - `dist/macos-amd64/cloudnest`
  - `dist/macos-arm64/cloudnest`

3. 构建 Linux 双架构
- `make build-linux`
- 输出：
  - `dist/linux-amd64/cloudnest`
  - `dist/linux-arm64/cloudnest`

### 3.2 不用 Makefile 的手动构建
1. macOS arm64
- `GOOS=darwin GOARCH=arm64 go build -o cloudnest ./cmd/server`

2. Linux amd64
- `GOOS=linux GOARCH=amd64 go build -o cloudnest ./cmd/server`

### 3.3 一键发布包（推荐）
可自动完成：
- 多平台构建（macOS amd64/arm64、Linux amd64/arm64）
- 写入版本信息（`cloudnest version` 可查看）
- 产出 tar.gz 包

命令：
- `make release VERSION=v1.0.0`

或直接：
- `./scripts/release.sh v1.0.0`

不传版本时，会尝试使用 git tag/commit 自动生成版本号：
- `make release`

发布产物目录：
- `dist/release/`
  - `cloudnest_<version>_darwin_amd64.tar.gz`
  - `cloudnest_<version>_darwin_arm64.tar.gz`
  - `cloudnest_<version>_linux_amd64.tar.gz`
  - `cloudnest_<version>_linux_arm64.tar.gz`

## 4. 部署后启动示例
1. Linux 服务器
- `./cloudnest 8080 /data/cloudnest`

2. macOS 本机
- `./cloudnest 8080 ./data`

## 5. 环境变量说明（仍可使用）
命令行参数优先于环境变量。

`.env` 加载顺序：
- 先读取当前工作目录的 `.env`
- 再读取可执行文件同目录的 `.env`（会覆盖同名项）

建议发布后做法：
- 将发布包中的 `.env.example` 复制为 `.env`
- 在 `.env` 中填写正确的 `MYSQL_DSN` / `REDIS_*` / `JWT_SECRET`

常用变量：
- `APP_PORT`
- `DATA_DIR`
- `MYSQL_DSN`
- `REDIS_ADDR`
- `REDIS_PASSWORD`
- `REDIS_DB`
- `JWT_SECRET`
- `JWT_EXPIRE_HOURS`


## 6. 登录限流与代理边界

`POST /api/auth/login` 在 JSON 解析/数据库/密码验证之前按实际 TCP 对端 IP 限制为每 60 秒 30 次。成功、失败及无效 JSON 都计数；超限返回 429 和 `Retry-After` 秒数。Redis 不可用返回 503，已有 Redis 认证机制仍是必要依赖。等待窗口自然过期即可恢复，不应清空 Redis 来解除限流，以免影响其他会话。

默认不信任 X-Forwarded-For、X-Real-IP、Forwarded 等转发头。共享出口、反向代理、FRP 转发可能使多个用户共享额度；操作日志与分享限流也使用实际连接 IP。部署需要区分代理后的真实客户端时，应在受控入口实施每客户端限流，并另行设计明确代理白名单；不要直接开启“信任全部代理”。本阶段没有放宽或关闭限流的环境变量，后续依据实际负载评估配置与账号级异常检测。

## 7. G02 文件命名升级

本批新增 file_namespace 表用于同目录命名事务锁。需停旧实例、备份和审核后显式 migrate，然后运行 audit-file-names，确认没有历史冲突/异常标量，再执行 migrate-file-names。后者安装独立版本化活动名称唯一索引和 CHECK，沿用现有文件名字符集/排序规则；普通启动验证完整约束定义及版本 checksum，不自动迁移。

迁移遇到历史问题会拒绝继续，不自动改名/删除用户条目。DDL 完成但版本记录缺失时，只在结构精确匹配后补记版本；部分/篡改结构不会被自动修补。不要混跑旧实例。完整步骤与中断恢复见 [名称约束迁移](../../docs/remediation/FILE-NAME-MIGRATION.md)。

上传、复制、移动和恢复重名时分配数字后缀，新建目录和重命名冲突返回 409；根目录按所有者隔离，共享父目录统一判重。ZIP/批量下载/复制/移动/永久删除逐项验证现有 ACL，详情见 [G02 报告](../../docs/remediation/G02-FILE-CONSISTENCY.md)。存储回收、配额、目录继承和上传幂等仍需后续验收。

## 8. 对象与版本升级

对象/版本整改新增 file_version.file_type/source_verified，需显式 migrate；普通启动缺失字段会退出。新上传使用独立不可变候选路径并在同事务记录初始版本，版本恢复追加新版本。必须停旧实例，避免旧代码继续覆盖/删除同任务路径；不能按 .upload-* 前缀清理对象。完整接口、迁移与 GC 前置限制见 [对象与版本报告](../../docs/remediation/BLOB-VERSION-CONSISTENCY.md)。

## 9. 存储引用保留约束升级

完成基础 migrate / 名称迁移后，还需在停旧实例、备份并审核副本的前提下运行 audit-storage-references → migrate-storage-references。两命令仅需 MYSQL_DSN；审计不读磁盘，发现悬空引用非零退出，不修历史记录。外键包含回收站和未知来源旧版本，均禁止级联删除。普通启动核对两步约束及 checksum，部分升级或漂移退出。跨表 DDL 非原子，中断恢复、foreign_key_checks 要求及仍未实现的物理 GC 边界见 [存储引用迁移](../../docs/remediation/STORAGE-REFERENCE-MIGRATION.md)。

## 10. 读取租约升级

需显式 migrate 增加 storage.state 和 storage_read_lease，普通启动核对列、索引与保留外键；旧对象默认 active，不移动/回收。不要混跑不持租约的旧实例。请求和后台分析各自续租，保护失败返回 503 或停止后续输出；清理失败可能留下到期行，目前没有自动过期清理或物理 GC。接口未增加用户可操作的租约参数。详见 [读取租约](../../docs/remediation/STORAGE-READ-LEASES.md)。

## 11. 显式托管与 GC 维护

新字段/回收记录需显式 migrate；旧对象默认未托管，不按前缀或年龄认领。gc-storage 需显式 DATA_DIR、独立维护账号的完整元数据可见性和既有约束，按两段 24 小时宽限期隔离、持久 tombstone 后删除隔离文件；普通启动和永久删除 API 不执行物理 GC。prune-read-leases 每次最多删除 256 条过期 token，不删盘。未部署自动任务。维护权限、未知引用/触发器拒绝、中断恢复、保留范围与尚未验收项见 [GC 协议](../../docs/remediation/STORAGE-GC.md)。先停旧实例、备份和副本演练，不能用 disposable 测试替代真实升级验收。

## 12. 容量账本与上传预留升级

显式 migrate 增加 user_storage_ledger、storage_quota_policy 单例和 upload_task 的合同/预留/目录/期限字段及索引；启动拒绝缺失结构或单例。停旧实例后再升级，旧 contract_version=0 任务不自动恢复为有额度预留的任务；旧分片保留，新客户端重新初始化。现有两个 quota 设置键仍按每用户额度使用，不是整机磁盘池；非法配置拒绝新分配，不能以失败回退无限制。定义、状态、507/409/503、取消/期限释放以及临时磁盘预算仍待 G03 的边界见 [计量与预留](../../docs/remediation/STORAGE-QUOTA.md)。没有对真实库执行升级。

### G03 上传完成回执升级

停旧写实例并备份、在副本验证后执行显式 migrate，新增 upload_task.result_version/result_file_id/result_json；普通启动只核对，不隐式迁移。旧已完成任务保留空结果，不按文件名猜回执；新完成任务重复请求返回原始确认，不代表当前文件还存在。详见 [G03 传输报告](../../docs/remediation/G03-TRANSFER.md)。未执行生产升级，稳定分片/资源预算及真实恢复演练仍待做。

### G03 不可变分片升级

停全部旧写实例、备份与副本演练后显式 migrate 增加 upload_task.chunk_protocol、upload_chunk.sha256/md5，并核对索引。旧未完成任务不自动认领分片，可取消释放逻辑预留，原字节保留；已完成的有效回执仍可复用。上传入口需要 Redis 脚本/TIME/ZSET/PEXPIRE 权限，HTTP writer 需支持读取期限；标准服务设请求读取超时 5 分钟，分片总期限 4 分钟。详见 [分片协议与资源边界](../../docs/remediation/STABLE-CHUNKS.md)，全局持久磁盘预算/崩溃清理尚未完成。

## G03 上传临时对象与容量

升级须停旧写实例与回收 worker，备份并在副本审核显式 migrate；新增持久候选登记和默认 0 的传输协议，不能自动认领旧进行中分片。DATA_DIR/storage 的控制文件绑定实际 MySQL server_uuid/数据库，不能单独删除以重新初始化额度；迁移根目录/数据库恢复须单独审核。仅支持本机 Linux/macOS 文件锁，不支持活跃克隆或网络文件系统。

TRANSFER_TEMP_LIMIT_BYTES 默认 8589934592，仅初始化新卷；现有额度使用显式 set-transfer-limit 修改。可选 TRANSFER_MAINTENANCE_DSN 指向相同实际数据库，专用于后台回收；需完整 schema SELECT/TRIGGER 可见性且无触发器，不自动授权。APP_BIND_ADDR 可设 127.0.0.1，默认空仍监听全部接口。

维护 audit-transfers / reconcile-transfers / set-transfer-limit 均要求显式 DATA_DIR 和 MYSQL_DSN，不要求 JWT/Redis。只读检查不创建未初始化卷；回收仅凭登记身份/锁/引用，blocked 保留并持续收费。JSON 不显示路径，有待审核项返回非零。完整语义、命令示例、分批上限及未验证的断电/恢复边界见 [登记与回收指南](../../docs/remediation/TRANSFER-REGISTRY.md)。本轮未操作真实数据库。

G03 后续支持 total_size=0 / total_chunks=0 的真实空文件，完成仍有最小临时登记及审计；此批不新增数据库列。必须整体更新写实例，旧二进制会把进行中的新零预留任务视作异常，不支持混跑或未核对任务直接回滚。现有未知旧分片不会被认领。协议和验证范围见 [空文件说明](../../docs/remediation/EMPTY-UPLOADS.md)。

G03 暂停/继续新增 upload_task/transfer_artifact.transfer_epoch（有符号 BIGINT NOT NULL DEFAULT 0），须停旧写实例和回收 worker、备份/副本演练后显式 migrate；普通启动字段缺失/漂移拒绝。旧二进制不执行代次隔离，不能混跑或直接回滚。详细控制命令、配额/检查点、在途请求与失败边界见 [暂停/继续协议](../../docs/remediation/UPLOAD-CONTROL.md)。

G03 下载身份批次不新增数据库字段，仍须满足整个 PR 的既有显式迁移要求。当前/历史/分享/预览读取现在在发送前校验完整尺寸和 SHA-256，旧 MD5/损坏元数据将拒绝而不自动重写；升级前应按既有只读审计核查，不能据此删除或自动认领旧对象。新缩略图键按源 SHA-256 隔离，旧缓存保留；视频/预览/缩略图统一执行下载策略。Range 续传须用强 ETag；日期 If-Range 回退完整 200，客户端不能追加旧片段。整文件预校验存在 O(N) IO 成本，大文件/并发容量尚未验收；详见 [下载协议](../../docs/remediation/DOWNLOAD-INTEGRITY.md)。
